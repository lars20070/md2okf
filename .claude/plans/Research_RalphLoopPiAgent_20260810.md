# Pi Ecosystem & the Ralph Loop: What to Install, What to Build, for md2okf

## TL;DR
- **Nothing in the Pi ecosystem is a drop-in fit for md2okf's sandboxed, host-driven fixpoint loop, but the closest ready-to-use option is a *host-side* agent-agnostic harness (frankbria/ralph-claude-code once its multi-provider adapter lands, or a thin bespoke script) — not a Pi extension.** Every existing Pi "ralph" package is an *in-session* driver that runs the loop inside one long-lived Pi process; that fights Pi's own known auto-compaction and context-overflow bugs, which is exactly the failure mode md2okf's fresh-context-per-pass design already avoids. This aligns with the canonical definition of the technique — Geoffrey Huntley ("Ralph Wiggum as a 'software engineer'", ghuntley.com/ralph, 14 Jul 2025): *"Ralph is a technique. In its purest form, Ralph is a Bash loop. `while :; do cat PROMPT.md | claude-code ; done` ... Ralph can be done with any tool that does not cap tool calls and usage."*
- **Pi has no `--max-turns`, `--max-tokens`, or cost/iteration cap flag** (feature request #1898 was closed unimplemented), and **no Stop-hook**. This is deliberate — Mario Zechner ("What I learned building an opinionated and minimal coding agent", mariozechner.at, 30 Nov 2025): *"The agent loop doesn't let you specify max steps or similar knobs you'd find in other unified LLM APIs. I never found a use case for that, so why add it? The loop just loops until the agent says it's done."* The nearest extension analog to Claude Code's Stop hook is the `agent_settled` event; a structured completion signal must be built as a custom tool (with `terminate: true`) plus a host-side parser of `--mode json`.
- **lars should keep the host-side bash loop, switch the driver to `--mode json` for a real stop signal, and add one tiny in-kit "coverage/mark-complete" tool** rather than adopt any third-party Pi loop package. Two Pi bugs bite the current design directly and must be worked around: `pi -p`/`--mode json` can hang instead of exiting (feed empty stdin via a pipe, not `</dev/null`), and skills/project config are silently ignored in non-interactive mode unless trust is pre-granted.

## Key Findings

### 1. The Pi package registry is huge but has no loop primitive built for external drivers
Pi's package catalog lists 5,342 packages (pi.dev/packages), installable with `pi install npm:<pkg>`. Packages bundle four resource types — extensions (TypeScript), skills, prompt templates, themes — declared in `package.json` under a `pi` key or via convention directories (`extensions/`, `skills/`, `prompts/`, `themes/`). There are many loop/queue/autonomy packages, but **all of them drive the loop *from inside* a running Pi session** via the `agent_end`/`agent_settled` events or a `ralph_loop` custom tool. None of them is designed to be invoked as `sbx exec md2okf -- pi ...` once per pass by an external shell script — which is md2okf's model.

Relevant loop/autonomy packages found:
- **`@tmustier/pi-ralph-wiggum`** (npm, git:github.com/tmustier/pi-extensions) — the most directly "Ralph" package. Sets up `.ralph/<name>.md` with a checklist, runs `ralph_start`, re-sends the same prompt on `ralph_done`, stops on `<promise>COMPLETE</promise>`. Explicitly "builds on Geoffrey Huntley's ralph-loop for Claude Code and adapts it for Pi." Can optionally invoke another Pi via tmux. In-session driver.
- **`pi-goal-list-loop-audit`** (npm, github.com/DraconDev/pi-goal-list-loop-audit) — the most sophisticated: `/goal`, `/list`, `/loop` commands, an `agent_end`-driven continuation loop with a 5-minute backoff cap, and a **detached, extension-less auditor RPC process** that independently re-verifies completions with raw evidence (`regression_shield`). Has a documented "Two-Driver Rule": any other extension that drives turns on `agent_end` conflicts. Notes hard conflicts with `pi-loop-mode`, `pi-goal-x`, `ralphi`, `pi-ralph*`.
- **`ralph-loop-pi`** / **`pi-hooks`** (npm) — exposes a `ralph_loop` tool for looped single/chain subagent execution until a condition returns false; supports max iterations and min delay. In-session tool.
- **`@rahulmutt/pi-ralph`** (npm:@rahulmutt/pi-ralph, github.com/rahulmutt/pi-ralph) — minimalist `/ralph <prompt-file>` that runs a prompt file repeatedly across **fresh branched sessions** (context cleared each iteration), persisting progress under `.ralph/` (RALPH.md summary + per-iteration JSONL). Closest in spirit to md2okf, but still in-session (uses `ctx.newSession`/`fork`, waits for idle).
- **`samfoy/pi-ralph`** (npm `pi-ralph`), **`@lnilluv/pi-ralph-loop`**, **`@narumitw/pi-goal`** (autonomous `/goal` with ordered queues), **`@reddb-io/red-skills-dev`** (autonomous `/afk` loop), **`@quintinshaw/pi-dynamic-workflows`**, **`@mjasnikovs/pi-task`**, **`@tangle-network/tcloud-agent`** (agent run-loop with criterion gates + budget caps) — all in-session drivers/orchestrators.
- **`@rhobot-dev/pi-ralph`** — a Pi TUI wrapper that *manages* mikeyobrien-style `ralph` loops (reads `ralph.yml`), i.e. a bridge to the external Rust `ralph`, not its own loop.

**Assessment:** These are category (ii) — "exist but would need adapting," and adapting is more work than it's worth for md2okf, because they assume an interactive/long-lived session with the TUI or RPC event bus, not a one-shot `pi -p` per document pass. They also each carry their own opinionated state directory (`.ralph/`, `.pi-glla/`) that would collide with md2okf's `okf/`-as-state design. Critically, building the loop as an in-session skill/extension undercuts the point of Ralph — as Michael Arnaldi puts it (quoted in ZeroSync's "The Ralph Loop: Long-Running AI Agents"): *"If you're implementing Ralph as part of the agent harness via skill/command/etc you are missing the point of Ralph which is to use always a fresh context."*

### 2. Pi's extension API: the events and hooks that matter for loop control
Pi extensions are TypeScript modules in `~/.pi/agent/extensions/` (global) or `.pi/extensions/` (project). The full lifecycle event list (from pi.dev/docs/latest/extensions) is:
- **Startup:** `project_trust`, `session_start`, `resources_discover`
- **Session:** `session_info_changed`, `session_before_switch`, `session_before_fork`, `session_before_compact`, `session_compact`, `session_before_tree`, `session_tree`, `session_shutdown`
- **Agent:** `before_agent_start`, `agent_start`, `agent_end`, **`agent_settled`**, `turn_start`, `turn_end`, `message_start`/`message_update`/`message_end`
- **Provider/model:** `context`, `before_provider_headers`, `before_provider_request`, `after_provider_response`, `model_select`, `thinking_level_select`
- **Tool:** `tool_execution_start/update/end`, `tool_call` (can block), `tool_result` (can modify)
- **Input/bash:** `input`, `user_bash`

**(a) Stop-hook analog.** Pi has **no exit-code-2 Stop hook** like Claude Code. The closest is **`agent_settled`**, which fires only when "Pi will not continue running automatically" (no retry, compaction, or follow-up left). An in-session Ralph loop can be built by having an `agent_settled` (or `agent_end`) handler inspect progress and call `pi.sendUserMessage(prompt, { deliverAs: "followUp" })` or `ctx.newSession(...).withSession(...)` to re-kick — this is exactly how `pi-goal-list-loop-audit`, `@tmustier/pi-ralph-wiggum`, and `@rahulmutt/pi-ralph` work. But this keeps everything in one process, defeating md2okf's fresh-context guarantee unless you fork a new session each pass (`ctx.newSession`/`ctx.fork`).

**(b) Custom tools as a completion signal.** Yes — `pi.registerTool()` registers LLM-callable tools. Critically, a tool's `execute()` can return **`terminate: true`**, which "hint[s] that the automatic follow-up LLM call should be skipped after the current tool batch" (takes effect only when every finalized tool result in the batch is terminating). This is the intended mechanism for a "mark section complete / report coverage" tool that ends a turn deterministically. See examples/extensions/structured-output.ts. State should be stored in tool result `details` (for branch-correct reconstruction) and/or written to disk.

**(c) `--mode json` stop signal.** `pi --mode json "<prompt>"` emits JSONL to stdout, one event per line. The first line is a session header `{"type":"session","version":3,"id":...}`. Then per-event: `agent_start`, `turn_start`, `message_start/update/end`, `tool_execution_start/update/end`, `turn_end`, `agent_end`, plus `queue_update`, `compaction_start`/`compaction_end`. `message_end` carries the final authoritative message including `usage` (tokens + cost). A host-side driver should parse this stream for: `tool_execution_end` of a custom "mark_complete" tool, `agent_end`, and cumulative token/cost from `message_end.usage`. This is a far better stop/progress signal than md2okf's current byte-count fixpoint.

**(d) Built-in budget/iteration caps: none.** As of August 2026 Pi's CLI has **no `--max-turns`, `--max-tokens`, `--max-iterations`, cost cap, or budget flag**. Feature request #1898 ("Add --max-turns and --max-tokens flags to pi --print") was **closed without implementation** (no linked PR; flags absent from current CLI reference). The only model-scoped control is `--thinking`. This omission is intentional, not an oversight — Zechner: *"The agent loop doesn't let you specify max steps or similar knobs you'd find in other unified LLM APIs. I never found a use case for that, so why add it? The loop just loops until the agent says it's done."* **Consequence:** iteration and budget capping must live entirely in the host driver — which md2okf already does via MAX_PASSES/MAX_RETRIES. Keep that; Pi will not do it for you.

**(e) Session flags in non-interactive mode.** `-c/--continue` (most recent session), `-r/--resume` (browse — interactive, not useful headless), `--session <path|id>`, `--fork <path|id>`, `--no-session` (ephemeral), `--session-dir <dir>`. In `-p`/`--mode json` these work but are largely unnecessary for md2okf: the whole point of the design is that **state lives in `okf/` on disk, not in a session**. Using `--no-session` per pass is the cleanest match (fresh context, nothing to resume), which is what md2okf effectively does. If you wanted cross-pass continuity you *could* use `--session <fixed-id>`, but that reintroduces the compaction/overflow risks below.

### 3. Prior art: people driving Pi headlessly in a loop
- **fsmiamoto/ralfinho** (blog: dorayaki.co, Feb 2026) — a purpose-built Ralph harness "building on top of the pi coding agent." The author explicitly notes Pi (unlike Claude Code) *can* stream raw text in non-TUI mode, and pairs it with his own sandbox tool `sb`. This is the closest published external-driver-for-Pi prior art and validates md2okf's architecture.
- **ralph-tui** (subsy/ralph-tui, ralph-tui.com) — has an official **Pi agent plugin** that invokes `pi --print --mode json --model ... < prompt.txt`, explicitly because "Pi outputs structured JSONL which enables detailed subagent tracing." Confirms `--mode json` is the sanctioned integration path.
- **nicobailon/pi-* extensions** — the "fresh eyes" review loop wrapped as a Pi extension (credited to Huntley's Ralph and doodlestein's prompt). In-session.
- **openclaw/openclaw** — the flagship real-world **SDK** integration (embeds Pi via `createAgentSession`), cited in Pi's own README as the reference for programmatic embedding. Relevant if lars ever wanted to drive Pi in-process from Node instead of shelling out — but that conflicts with the sandbox boundary.
- **badlogic/pi-share-hf** — publishes Pi sessions to Hugging Face datasets; only relevant if lars wants to share OSS sessions, not for looping.

**Maintainer position (Mario Zechner / badlogic).** Pi's design is deliberately minimal: the README and usage docs state it "intentionally does not include built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background bash. You can build or install those workflows as extensions or packages, or use external tools such as containers and tmux." The published npm README is blunter still: *"No background bash. Use tmux. Full observability, direct interaction. Read the blog post for the full rationale."* On sub-agents specifically, Zechner's blog (mariozechner.at, 30 Nov 2025) argues *"Bash is all you need... If you need pi to spawn itself, just ask it to run itself via bash... inside a tmux session for full observability."* **Interpretation:** the maintainer's stated preference is that long-running/looped/unattended orchestration lives *outside* the core — as an external driver (containers, shell, tmux) or SDK program — not baked in. This directly endorses md2okf's host-side `compile-wiki.sh` approach over an in-session extension.

### 4. Open Pi bugs/limitations that bite an unattended looped design
Note: earendil-works/pi mass-closes issues during refactors (labels like `closed-because-bigrefactor`, `closed-because-weekend`), so "closed" ≠ "fixed/verified." Each item below affects a Ralph driver:

- **#4303 — `pi -p --mode json` never exits when stdin is `/dev/null`** (state: Closed; labels bug, closed-because-bigrefactor, closed-because-weekend; assignee mitsuhiko). **This is the single most dangerous bug for md2okf**, which pipes `</dev/null`. Verbatim repro: `timeout 15 pi -p --mode json "say hi" < /dev/null` → exit 124 (hangs); `echo "" | timeout 15 pi -p --mode json "say hi" < /dev/null` → exit 0. **Workaround:** feed empty stdin through a pipe (`echo "" | sbx exec ... pi ...`) instead of `</dev/null`, or ship an extension that hooks `agent_end` and calls `process.exit(0)` when `!process.stdin.isTTY`.
- **#161 / #3011 / #2195 — print mode not exiting** (all Closed). #2195 is specifically "hangs indefinitely when extensions emit steer messages" during `session_start` — meaning any extension in the kit that sends a steer/announce message on startup can wedge `pi -p`. Root cause: `prompt()` called while agent still streaming steer response. Workaround for that variant: `--no-extensions`, or ensure kit extensions don't emit startup steer messages.
- **#2078 — InteractiveMode/ProcessTerminal hangs on non-TTY stdin** (no isTTY guard). Relevant because a mis-set flag can drop pi into interactive mode with no TTY and hang silently with no output/exit code — a worst-case for unattended runs.
- **#1898 — no `--max-turns`/`--max-tokens`** (Closed, unimplemented). Consequence: no per-invocation turn/budget cap; the host loop must own all limits.
- **#2871 / #6879 / #1796 / #128 / #7020 — auto-compaction timing/overflow bugs.** Auto-compaction is only checked at `agent_end` and before the next prompt, **not mid-turn**, so a single long tool-looping turn can blow far past the context window (observed >200%, and >370k on a 272k model) before the provider hard-rejects, wasting tokens and sometimes bricking the session (#1796) or returning control instead of continuing (#7020). **This is a strong argument for md2okf's short, fresh-context passes** — each `pi -p` pass should do a *bounded* amount of work and exit, keeping any single turn well under the window. Do not let a single pass try to compile the whole wiki.
- **#5194 / harness-v2 tool-arg truncation.** Tool-call arguments can arrive empty/truncated at the model-output/transport boundary; the built-in `edit` tool then reports a misleading "missing required properties" and the model retries the identical failing call repeatedly, burning a pass. The harness treats an output-limit `length` stop mid-tool-call by appending `isError` results per call. **Consequence:** a pass can "fail" in a way that produces no `okf/` bytes yet exits nonzero — md2okf's retry-with-backoff handles this, but the byte-fixpoint stop could misfire if a truncated pass looks like "no progress."
- **#6994 / #6206 — output-token caps.** llama.cpp provider hardcodes maxTokens 16384; clamping maxTokens to contextWindow can trigger spurious "maximum output token limit" errors. Only relevant if lars uses a local/gateway model with a small window.
- **Non-interactive project trust / skills loading.** Per usage docs: "Non-interactive modes (`-p`, `--mode json`, `--mode rpc`) do not show a trust prompt." Without a saved decision they fall back to `defaultProjectTrust` (default `ask` → **ignores project resources**). Project-local `.pi` extensions/skills/settings load **only after trust is resolved**. **Consequence for md2okf:** because config is delivered in the kit at `~/.pi/agent/` (the *global/user* location, copied into the sandbox home), the compile-wiki skill lives at the user scope and loads fine; but if any resource were project-local (`.pi/` in the repo), it would be silently dropped in `-p` mode unless the driver passes `--approve`/`-a` or sets `defaultProjectTrust: always`. Recommendation: keep everything user-scoped in the kit (as md2okf does) and/or pass `-a`.

## Details: concrete recommendations for md2okf

### What exists today and is ready to use (category i)
- **`--mode json` as the driver's I/O contract.** Ready now. Switch `sbx exec md2okf -- pi -p "<prompt>"` to `pi --mode json "<prompt>"` and parse stdout. This gives a real progress/stop signal (a `tool_execution_end` for your completion tool, `agent_end`, and `usage`) instead of the brittle `wiki_size()` byte-fixpoint. This is the sanctioned integration path (ralph-tui's Pi plugin uses exactly this).
- **The host-side bash loop itself.** Keep it. It already implements fresh-context-per-pass, disk-as-state, iteration cap, and retry/backoff — all things Pi deliberately does not provide and the maintainer explicitly pushes to external drivers.

### What exists but needs adapting (category ii)
- **`@rahulmutt/pi-ralph`** is the single package whose philosophy matches md2okf (fresh branched session per iteration, `.ralph/` progress on disk). If lars ever wanted the loop *inside* one Pi process, this is the closest — but it's in-session and would duplicate the sandbox/host loop lars already has. Not recommended for the current architecture.
- **Th0rgal/open-ralph-wiggum or michaelshimeles/ralphy** — if lars wants to *replace* his bespoke bash loop with a maintained one, these are the lowest-effort adapters (add a `pi` branch to their `--agent` switch, calling `sbx exec md2okf -- pi --mode json`). Trade-off: they assume a `<promise>DONE</promise>` marker convention rather than a byte-fixpoint, which is arguably *better* — but they weren't written with a microVM boundary, so lars would still own the `sbx exec` wrapping.
- **frankbria/ralph-claude-code** — worth tracking. Once the agent adapter contract (ADR 0002) ships, a `lib/agents/pi.sh` adapter is the most robust long-term option, and its Docker-sandbox posture matches md2okf. Not ready today.

### What does not exist and must be written (category iii)
1. **A "coverage / mark-complete" custom tool**, shipped in the kit at `pi/files/home/.pi/agent/extensions/`. It should (a) let the model report per-document/per-section coverage, (b) write that state into `okf/` (or a sidecar like `okf/.coverage.json`) so it survives the fresh context, and (c) return `terminate: true` when the current document is fully compiled, giving the driver a deterministic end-of-pass signal in the JSON stream. This is ~30–60 lines of TypeScript using `pi.registerTool`. Because the kit is **copied, not mounted**, it must be installed at kit-build time (add it to `pi/files/home/.pi/agent/extensions/` before `sbx run --kit`), and any npm deps must be vendored into the kit (no runtime `npm install` — the sandbox network allowlist and proxy-managed OpenRouter key mean runtime package installation will fail).
2. **A JSON-stream parser in `compile-wiki.sh`** that reads the `--mode json` output, extracts the completion-tool signal and token/cost usage, and decides stop/continue — replacing or supplementing `wiki_size()`. Belongs on the host, alongside `compile-wiki.sh`.
3. **An `agent_end` force-exit guard extension** (the #4303 workaround) in the kit, OR switch the driver to pipe empty stdin (`echo "" | sbx exec ...`). Pick one; the empty-stdin pipe is simpler and needs no kit change.

### Sandbox-specific conflicts to flag
- **No MCP in Pi** — irrelevant here (don't install MCP-adapter packages like `pi-mcp-adapter`); the completion tool is a native extension tool.
- **Network allowlist in `pi/spec.yaml`** — any package that fetches at runtime (web-search packages, remote memory servers, `refreshModels` providers) will fail. Keep the kit self-contained.
- **Proxy-managed OpenRouter key** — extensions that register their own providers or auth flows are unnecessary and may conflict; rely on the kit's `models.json`/settings.
- **Config copied not mounted** — everything (skill, extension, settings) must be baked into the kit before `sbx run`. `pi install` at runtime is out (needs network + writes to `~/.pi`).
- **User-scoped config avoids the trust trap** — because the kit places config in `~/.pi/agent/` (user scope), the compile-wiki skill loads in `-p`/`--mode json` mode without a trust prompt. Do not move config to a project-local `.pi/`; it would be silently ignored non-interactively unless `--approve` is passed.

## Recommendations (staged)

**Stage 1 — de-risk the current loop (do first, no new deps).**
1. Replace `</dev/null` with an empty-stdin pipe to dodge the #4303 hang: `echo "" | sbx exec md2okf -- pi -p "<prompt>"` (or add the `agent_end`→`process.exit(0)` guard extension to the kit). Benchmark: if any pass ever exits 124/times out, this bug is active.
2. Ensure no kit extension emits a startup steer message (avoids #2195). If you see `pi -p` hang right after "session_start," suspect this.
3. Keep MAX_PASSES/MAX_RETRIES — Pi has no budget flags and won't get them (#1898 closed).

**Stage 2 — replace the byte-fixpoint with a real signal.**
4. Switch the driver to `pi --mode json`, and add the in-kit **mark-complete tool** returning `terminate: true`. Stop the per-document loop when you see that tool's `tool_execution_end` (not when byte count stops growing). Keep `wiki_size()` only as a secondary safety net. Benchmark to change approach: if the model won't reliably call the completion tool, fall back to the byte-fixpoint + a `<promise>DONE</promise>` string check in the final `message_end`.
5. Parse `message_end.usage` from the JSON stream to log per-pass tokens/cost and enforce a real budget cap in the host loop.

**Stage 3 — only if you outgrow the bespoke script.**
6. Evaluate migrating the loop skeleton to **Th0rgal/open-ralph-wiggum** or **michaelshimeles/ralphy** (add a `pi` agent branch wrapping `sbx exec`), or wait for **frankbria/ralph-claude-code**'s agent-adapter contract and write `lib/agents/pi.sh`. Change trigger: when maintaining the bash loop's stop/retry/parsing logic becomes more work than adopting a maintained harness.
7. Do **not** adopt in-session Pi loop packages (`@tmustier/pi-ralph-wiggum`, `pi-goal-list-loop-audit`, `ralph-loop-pi`) for this architecture — they fight the fresh-context model and Pi's mid-turn compaction bugs (#2871, #6879), and duplicate the disk-state loop lars already owns.

## Caveats
- **"Closed" ≠ "fixed"** on earendil-works/pi: the repo mass-closes issues during refactors (labels `closed-because-bigrefactor`, `closed-because-weekend`) and auto-closes new-contributor issues. I could read issue bodies/state/labels but not comment threads, so whether the print-mode hang (#4303, #161, #3011, #2195) is actually fixed in the current release is **unconfirmed** — treat the empty-stdin workaround as necessary until you verify on your pinned Pi version.
- Pi's docs do **not** publish an explicit exit-code contract for print mode; the strongest evidence that `pi -p` returns non-zero on error/abort/length is the official `pi-sub-agent` package doc, not a core doc. Verify exit codes empirically against your model/provider before relying on them for retry logic.
- Package download/star counts and the 5,342 package total are point-in-time (pages were served from caches of varying age); treat magnitudes as approximate.
- I did not find any *official* Earendil/Pi first-party Ralph package or first-party statement endorsing a specific Ralph implementation — the maintainer's position is inferred from the "minimal core / use external drivers, tmux, containers" design statements (mariozechner.at and the npm README), which is consistent but not an explicit "here's how to Ralph Pi" doc.
